# Cockpit — reference

The complete reference: every feature, the configuration keys, the layout of the code and the security model. For a quick start, see the [README](../README.md).

> **Warning.** The cockpit gives whoever holds its access token a shell on the machine it runs on, and lets them drive your Claude Code sessions. Keep its port on a network you trust, never share the URL printed by `start.sh`, and read [Security](#security) before exposing it.

A small web cockpit to follow and drive parallel Claude Code sessions started with `claude --worktree`.

For each git worktree it shows the Claude session state (working / needs input / done), the conversation, the live terminal, the changed files and their diff. Sessions running in tmux can be driven from the browser: send messages, answer permission prompts, switch permission mode, start or resume a session, close a worktree. A persistent bash terminal is available as its own card.

"New session" can start a **review** session instead of a free one: give it a pull request, and the session starts with a system prompt that lists the review skills to load (`code-review`, `security-review` and every skill whose name contains "review", or `review.skills` in the config) and asks for a report through the `review-report` skill. The report (`~/.claude/worktree-reviews/<worktree>.report.json`) is shown in a "Rapport" tab as colored blocks: blocking (red, request changes), to fix (amber), suggestion (blue), question (violet), praise (green), context (grey), each with its finding, impact, fix and a draft PR comment to copy.

When an app is configured, every side panel also carries an app button and an App tab: they run the app's launch command once at the root of the main checkout (tmux session `cw-app`) and show its state — stopped, building, starting, up, degraded or KO — with the launch log, restart and stop.

A "Tokens utilisés" card shows how much of the account's usage limits is used (5-hour and 7-day windows, spend limit when there is one) with their reset time. It turns amber at 80 % used and red at 95 %, and the header then shows the limit as an alert. Worktree cards show a "Contexte" chip when 20 % or less of their session's context window is left. The card opens a Tokens tab with the used and remaining share of each limit, each session's remaining context and estimated cost, the tokens processed per day over 7 days and the usage per worktree. Limits, context and cost come from what Claude Code sends to the status line: `statusline.js` writes one snapshot per session in `~/.claude/worktree-usage/`, so the limits shown are those of the last Claude answer. The daily history is read from the transcripts in `~/.claude/projects/` (subagents included).

### Parallel worktrees

Each session works in its own worktree (`<repo>/.claude/worktrees/<name>`, created by `claude --worktree`, the cockpit or `bin/ctx`), next to the others, on resources they share (databases, the running app). The `worktrees` section of `cockpit.config.json` describes what that means for the repo, and the cockpit applies it:

- `include`: files Claude Code copies into a new worktree (typically `.env`). `install.js` writes them to the repo's `.worktreeinclude` (with a first comment line marking it as the cockpit's) and adds it to `.git/info/exclude`; a `.worktreeinclude` the repo versions, or one written by hand, is left alone (move its entries to `worktrees.include` and delete it to hand it over).
- `rules`, `setup`: at session start in a worktree, the `worktree-context.js` hook tells the session to load the `worktree-session` skill (generic rules), lists the repo's rules, and says which setup is missing (for example `node_modules`).
- `forbidden`: the `worktree-gate.js` hook refuses the matching Bash commands in a worktree (regular expressions, case-insensitive), with the label as the reason.

Both hooks only act in worktrees of the configured `repo` (of any repo when `repo` is not set). A repo that already has its own worktree hooks or a project `worktree-session` skill should drop them: the project skill would shadow the cockpit's, and both hooks would inject their context (`install.js` warns about the skill). `bin/ctx [TICKET-123 | "#5678" | name] [prompt]` opens a session in a new worktree of that repo from a terminal.

### Workstation layout

The page is a workstation for a full working day. On the left, the **attention queue** lists every worktree grouped by what you are expected to do: *À toi* (a permission or a question, oldest first), *À relire* (a finished turn), *En cours*, *Au repos*; each row says why. `j`/`k` walk it, `[` folds it to coloured dots. The selected session fills the centre: a one-line header (state, reason, the actions that state calls for, `d` for the details, ⋯ for every worktree action), its tabs and a compact composer whose `⚙ model · effort · mode` pill opens the session settings. The Changements tab shows the uncommitted lines added and removed (`+N −M`), and `f` hides the queue (focus mode). The top bar holds clickable state pills, the terminal, the token limits, `Ctrl K` and a ⋯ menu (tools, theme). History, cleanup, automations and skills open as pages in the centre, with their own address.

### Attention and triage

- **Notifications.** A background loop (every 3 s, even with no page open) turns session transitions into events: permission asked, question asked, turn done, CI failing, PR merged, app KO, automation run. They show as short pills in the header (card name and state, full text on hover, click to open the session), and the card that just finished gets a green ring until it is opened. The tab title carries the number of sessions waiting for you and the favicon turns amber. With `notify.ntfyUrl` set, events are also posted to an ntfy topic for phone push.
- **Pins.** "Épingler en tête de file" in the ⋯ menu of a session keeps its worktree on top of its queue group.
- **Keyboard.** `Ctrl K` opens a command palette; `j`/`k` move between queue rows, `a` allows the pending permission, `1`-`9` switch tabs, `n` new session, `h` history, `?` help.

### Questions answered in the conversation

When Claude asks a question (`AskUserQuestion`) in a session launched or resumed by the cockpit, the conversation shows a card with every question, its options and their descriptions, multi-select and a free answer; "Répondre" sends the answers to Claude, and the terminal never shows the dialog. Under the hood the `ask-relay.js` hook (`PreToolUse` on `AskUserQuestion`, given by the cockpit to every Claude session it launches or resumes with `--settings`, so nothing is added to `~/.claude/settings.json`) holds the question in `~/.claude/worktree-asks/` and answers Claude with `updatedInput` once the cockpit writes the answer (Claude Code 2.1.85 or later). "Répondre dans le terminal", no answer within 25 minutes, or a session started outside the cockpit (the cockpit marks its own with `COCKPIT_ASK=1`) leave the usual terminal dialog. Permission prompts get a card too (Autoriser, Toujours, Refuser, with the provider's keys; for a Claude session "Toujours" allows this one request, then, once the prompt is cleared (never before: a mode switch relaunches a session blocked on a prompt, which would kill the command just allowed), puts the session in auto mode, without saving a permission rule; a member of an orchestration takes its whole team along since an agent is never looser than its orchestration, and the other agents blocked on a prompt are relaunched in auto, conversation kept; a session that is not asking refuses the click), and so do questions of sessions the relay does not cover, whose options are typed into the terminal.

### Steering several sessions

- **One send, routed for you.** The composer has a single "Envoyer", like the CLI: the message always reaches the session, and while Claude works it is taken into account during the turn (Claude Code queues it itself). While Claude waits on a question or a permission, the message is held and leaves right after the answer. When a long message is sent to a busy session, a small model (`claude -p --model haiku`, about 2 s, `server/core/routing.js`) reads it against the current task: a clearly independent task starts a new session in the same worktree instead, and a toast says why. Short messages, follow-ups and slash commands skip that check.
- **Variants.** "Nouvelle session" can start N worktrees with the same prompt to compare approaches.
- **Delegation.** "Déléguer" on a Claude message starts a linked session pre-filled with that context. Cards show the parent and child links, and the parent can be told when the child finishes a turn.
- **Automations.** "Outils → Automatisations" starts a session with a prompt every day at a set time or every N minutes, in a fixed worktree or a new dated one.

### Providers: Claude and GPT

Sessions and agents run on a **provider**: Claude Code by default, or GPT through the OpenAI Codex CLI (`npm install -g @openai/codex`, then sign in from "⋯ → Connexions"). "Nouvelle session" picks the provider, its model, effort and permissions; a master can launch GPT agents with `orchestrate launch --provider codex --model <model>`. A GPT session gets the same queue row, conversation (read from its Codex rollout), changes, terminal and approval buttons as a Claude one, tagged "GPT".

The cockpit tracks a Codex session with the same state hook as Claude Code, passed with `-c hooks.<Event>=…` when it launches the session. Before those hooks run, Codex asks, once per repository, to trust the folder, and once for the cockpit's hooks (trust kept per hook content, so after the cockpit moves or its hook changes it is asked again); it may also offer an update. The cockpit remembers the Codex sessions it launches (`~/.claude/worktree-codex-launches.json`), reads the screen of those not attached to a state yet and shows the prompt in the queue and the conversation, with its options as buttons; a choice is relayed with arrow keys and Enter, so Codex makes and saves the decision itself. When no prompt shows and the hooks are not trusted yet, "Ouvrir la revue des hooks" types `/hooks` for you. "⋯ → Connexions → Autoriser GPT sur un dépôt" starts a bare Codex session in a chosen repository to go through these prompts before any work. Codex sessions started outside the cockpit are not tracked. Permission modes map to Codex sandboxes: plan → read-only, default and accept edits → workspace-write with approval on request, auto → `--approve-for-me`; the cockpit never bypasses approvals or sandboxes. `providers.codex.bin` (or `CODEX_BIN`) sets the Codex binary; `GET /api/providers` lists the providers, whether Codex is logged in and its model catalog.

### Relevance matrix

A master picks each agent's provider, model and effort from a **relevance matrix**: for each kind of task (explore, summarize, implement, frontend, tests, refactor, debug, delicate change, architecture, review, very large context), ranked picks with a reference score from 1 to 5 stars and the reason, plus each model's cost, speed and context. The shared matrix is versioned in the repo, in four files of `server/data/`: `model-matrix.json` (the hand-written default), `model-matrix-edits.json` (category edits published by the maintainer, which replace a default category), `model-verdicts.json` (the verdict records, one JSON record per line, see below) and `model-ratings.json` (the old 1-5 ratings, frozen: nothing writes them any more). Every install starts from that latest version.

Only the maintainer's cockpit writes these files: set `"matrix": { "maintainer": true }` in `cockpit.config.json` (only someone allowed to push to the repo should). There, edits and verdicts go straight into the repo files and the cockpit publishes them by itself: once the matrix has been quiet for 90 s (an Arène run that records five agents makes one commit), it commits the data files (`model-matrix-edits.json`, `model-verdicts.json`, and `model-ratings.json` when an older install changed it) on top of `origin/<default branch>` in a temporary index and pushes, with a message such as `chore(matrix): publish 3 verdicts (debug, review)`. The commit holds nothing else: other local changes and unpushed commits stay local. It is a three-way merge against the checkout's `HEAD`: only the categories and verdict records (key: the record `id`; an `outcome` record replaces the earlier one with the same id; the retention below applies) that changed locally since `HEAD` are published, everything else keeps the remote's version, so a checkout behind the remote never reverts it. The check also runs once at every start. The checkout's branch moves to the new commit when it sat on the published base, with no merge, rebase, cherry-pick or revert in progress; otherwise it is left for its owner to merge (the data files then stay modified until that merge, and `git pull` may ask to commit or discard them first). A failed fetch or push is retried every 5 minutes, and a `matrix_publish_failed` event appears after three failures in a row. Switching an install to maintainer mode does not migrate its `~/.claude` edits and ratings: copy them into the repo files first. Older installs ignore `model-verdicts.json`.

A local edit identical to the category it replaces is ignored, so that it never hides later published changes. Everywhere else, edits made on the "⋯ → Matrice des modèles" page are kept in `~/.claude/worktree-matrix.json` and win over the shared matrix, category by category ("Revenir au défaut" drops them), and verdicts go to `~/.claude/worktree-matrix-verdicts.json`, counted together with the published ones (the coverage queue is local too, in `~/.claude/worktree-matrix-coverage.json`, see below).

The matrix learns from **verdicts**, not from a master's opinion. A master launches an agent with `--kind <category>`; agents launched with a verification mission (`orchestrate launch … --verifies <role>:<ids>`, roles `reviewer`, `challenger`, `judge`, `consumer`; `orchestrate verifies <id> <role>:<ids>` adds targets to a live agent) end their final message with a verdict envelope (format: `skills/agent-protocol`). The quality of a pick is a score out of 100 computed from those identified findings; the master only records an **outcome** (`orchestrate outcome <id> as-is|fixed|partial|redone ["note"]`), shown beside the score and never mixed into it. `orchestrate rate` fails with a pointer to `outcome`. Cost always means tokens against the usage limit; no money amount is computed or shown.

**Verdict capture.** When an agent with a mission finishes, the cockpit reads its **final message of the turn** from the raw transcript (Claude: the last assistant text and its uuid; Codex: the turn's final agent message and its id; stored on the agent, 20,000 characters at most). Only a trailing envelope counts: the last non-blank line is `</verdict-report>`, the opening `<verdict-report v="1">` starts a line outside a code fence; quotes and examples earlier are ignored. Lines are accepted only if the writer's mission covers the target with a matching role (`rank` needs `judge`; a triage is accepted from a mission covering the finding's target or its judge, or from the finding's own target as `author`). Always rejected: about oneself, about an ancestor (parent chain), unknown ids, a `dup` across deliveries or a `missed` on a reviewer that never judged that target. The master's wake-up gets `Verdicts : 4 constats sur w1, w2 propre, 2 triages` and one `Ligne ignorée : <reason>` per rejected line; a transcript that arrives late is re-read at 5 s then 20 s, and `orchestrate verdicts --capture <id>` re-reads it (answers `travaille encore`, `pas encore dans son transcript` or `déjà enregistré`; it is refused while the agent works, never re-accepts a processed message and never accepts typed facts). Only the final message of a finished turn is captured. A turn counts as finished when its last Claude assistant entry has a `stop_reason` other than `tool_use`, or when Codex emitted `task_complete`. Finding texts and the outcome note are cleaned before storage (home paths, UUIDs). `orchestrate verdicts [id]` lists the job's findings, triages and contests. Routes: `POST /api/orch/outcome`, `/api/orch/verifies`, `/api/orch/verdicts/capture` and `GET /api/orch/verdicts` (`POST /api/orch/rate` only answers with the replacement message). Every agent gets an `obs` id (32 hex characters) at launch, the only key between records and usage rows (measures dedupe by `obs`, the latest wins); no session id or worktree is written in `model-verdicts.json`.

**What is and is not guaranteed.** Guaranteed: a stored verdict was written, as stored, in the final message of an agent the master launched with that mission, which is neither the target nor one of its descendants. Not guaranteed: that the master briefed the verifier honestly or picked a careful one. The briefs stay readable, reviewers get their own score, and later verifiers can record what an earlier reviewer missed (`missed=`, accepted only for a reviewer named in the writer's own `--verifies` mission).

**Scores.** Findings are `blocking`, `to-fix` or `suggestion`. A finding counts against its target unless its latest independent triage (a challenger, another reviewer, an Arène judge, a consumer; its severity replaces the stated one) says `false`, it is a `dup` of a finding on the same delivery of the same target, or it is a `suggestion` (recorded and shown, never scored). The author's triage `confirmed` is an admission and counts as a triage; `false` is only a contest (shown as contested, still counted until an independent triage settles it); `plausible` changes nothing. A residual after a new delivery is a new finding.
- Work agent (any kind but `review`): `D = 10 · blocking + 1 · to-fix` over counted findings, `score = round(100 · 0.96^D)`: a clean delivery 100, three to-fix 88, one blocking 66, one blocking and three to-fix 59.
- Reviewer (`review`): evaluated only when one of its findings was triaged independently or admitted, or a later independent verifier judged the same target. `C` = confirmed weight, `F` = weight of findings triaged `false`, `M` = weight of findings by later verifiers marked `missed=` this reviewer and not false (blocking 10, to-fix 1, suggestion 0): `score = round(100 · (C+1)/(C+F+1) · (C+1)/(C+M+1))`. Contested and untriaged findings are in neither `C` nor `F`.
- Observation levels set the weight: `audited` 1 (a finding triaged or admitted, two distinct verifiers, or an Arène judge), `reviewed` 0.6 (one verifier, findings, none triaged), `clean-unaudited` 0.3 (one verifier, only `clean`), evaluated reviewer 1; `outcome` 0.2 (no verifier: `as-is` 80, `fixed` 65, `partial` 45, `redone` 15) and legacy ratings 0.2 (1→20, 2→40, 3→55, 4→75, 5→90) count as unverified evidence.
- A pick's score `S = (3·ref + Σ wᵢ·sᵢ) / (3 + Σ wᵢ)`: the reference (the pick's stars through the same map; off-matrix 55) counts as weight 3, and unverified evidence weighs at most 1.5 in total per pick. `V` is the summed weight of verified observations; confidence is `à éprouver` below 1, `faible` below 3, `moyenne` below 6, `solide` from 6, and outcomes and legacy ratings never raise it. One perfect audited run on a 75 reference gives 81. Off-matrix combinations appear from V ≥ 1.
- Legacy ratings (`model-ratings.json`, `~/.claude/worktree-matrix-ratings.json`) are read only, with their weight capped as above, and their tokens and durations still feed the measures. Already published legacy ratings keep whatever they contain; freezing stops new ones.
- Retention: at most 5000 observed agents; the oldest are dropped with every record that references them.

**Ranking.** On value: among available picks whose score reaches 70 (good enough) and that are worth it (within 10 points of the best available score, or further behind but at most 75 % of the best-scored pick's quota cost), the lowest quota cost comes first, then the fastest, then the best score, then the key; the others follow by score, unavailable providers last. A category with `"rankBy": "quality"` (`delicate`, `architecture`, `debug`) puts in front the available picks within 3 points of the best score, ordered the same way, so the order cannot cycle. Quota cost is a **proxy**: the pick's median measured tokens (billed tokens, cache reads counted at 0.1) times the model's static `cost` tier, not a measured quota. Measures come from the usage store and from the tokens and duration recorded with each outcome; a pick with fewer than 2 measures takes the category's median tokens and duration, so it is not favoured. `orchestrate matrix` shows each pick's score /100 with its confidence, tokens, duration, measured count and, apart from the score, the outcomes, median rounds, Arène ranks and legacy average; the page lists "Verdicts récents". Picks of a provider that is not available (Codex not logged in) come last. Routes: `GET /api/matrix`, `POST /api/matrix/category`, `POST /api/matrix/reset`.

**Coverage queue.** Local state `~/.claude/worktree-matrix-coverage.json` (`launches`, `credits`, `spent`), across jobs and masters: every `orchestrate launch` adds 1, every 5th earns a credit, 2 banked at most (a corrupt file counts as zero). `orchestrate matrix <category>` shows the candidate when a credit is available: the available pick with a reference of 3 stars or more and the lowest `V` (ties: lowest quota cost); a pick with V ≥ 3 and a score at least 15 below the category's best, at no lower cost, is dominated and leaves the queue until every other pick also has V ≥ 3. `orchestrate launch --explore --kind <category>` is accepted only for that candidate and spends the credit; the agent is flagged as an exploration, and one with no verdict stays listed by `orchestrate status` as `exploration non vérifiée`, even after its outcome. In a value category the candidate takes the first pick's place; in a quality category it is a **duel** next to the first pick on the same brief, judged by an agent launched with `--verifies judge:<a>,<b>`, allowed only for a short task (`--minutes` at most 15), never from a sub-orchestrator, and while the candidate provider's 7-day window is under 50 %. `orchestrate send <id> --info "…"` sends a message that is not a correction; every other message after an agent's first delivery counts as a round.

**Arena mode** (`arena` setting of an orchestration, off by default; checkbox « Mode Arène » when creating a master and in the orchestration's Réglages, `orchestrate calibration on|off` from the CLI; the master header shows an « Arène » chip): while on for that orchestration, its master run each task that needs a model as a competition between several models and a judge, under its own verification mission, has them judged (findings and a rank per competitor, recorded apart from the score), until every available pick with a reference of 3 or more has a verified weight V of 3. `orchestrate calibration` shows the state of the caller's orchestration, the coverage and the missing combinations, and `orchestrate status` reports the mode in its header; circuit breaker: as soon as the fullest usage window (`five_hour` or `seven_day`, Claude or Codex, ignoring a window already reset) reaches `arena.maxUsagePercent` of `cockpit.config.json` (75 by default), the tick switches Arena off in every live orchestration, tells each master why and logs an `arena_cut` event; while over the threshold, `orchestrate calibration on`, the Réglages checkbox and the creation of a master with Arena are refused with that reason; it is never switched back on automatically. `orchestrate rescore <category> <provider>:<model>:<effort> <1-5> "<reason>"` does not change the matrix: it records a pending proposal (a new reference score and reason for a pick, or its addition, 8 picks at most per category) that the user validates, rejects or, once validated, cancels in the « Matrice des modèles » page; validating writes it as a local edit, cancelling restores the previous value unless the category changed since. The judge is Claude opus at medium, never a competitor; a scoring sheet it launches under `--verifies judge:<ids>` scores the anonymised outputs (a GPT leaf when all competitors are Claude). Routes: `GET /api/calibration` (coverage), `GET`/`POST /api/orch/arena`, `POST /api/orch/rescore`, `POST /api/matrix/proposal` (`decision`: validate, reject or revert; refused when it carries a `caller`).

### Connections: AI providers and MCP servers

"⋯ → Connexions : IA et MCP" gathers everything the cockpit connects to.

- **AI.** Claude and GPT each show whether they are signed in (account, method, expiry). Sign-in works from the container, without a browser on it: GPT with a ChatGPT account runs `codex login --device-auth` and the page shows the link and the one-time code to enter on any device, then notices when it is approved; GPT can also take an OpenAI API key, handed to `codex login --with-api-key` on stdin and never stored by the cockpit; Claude runs `claude auth login` (subscription or Anthropic console), the page shows its link and takes the code its page gives back. Each sign-in runs in its own tmux session (`cw-login-claude`, `cw-login-codex`).
- **MCP servers, for the whole application.** There is no per-worktree context: a server added here goes to Claude's user scope and to Codex's global config (Claude and GPT by default), so every session of every worktree gets it. The list groups claude.ai connectors, Claude, Claude plugins and GPT, marks the servers both providers have, and shows each one's transport, target, the names of its env variables and headers (never their values) and its health (`claude mcp list`, run in the background and cached 5 minutes). "Aussi pour GPT" / "Aussi pour Claude" copy a server to the other provider server-side (secrets included, never through the page). Servers a repository declares (its `.mcp.json`, or Claude's local scope, kept per main repository) are listed apart: "Rendre global" copies one to the user scope. "Se connecter" types an MCP server's OAuth login into the terminal; "Retirer" removes a server. Routes: `GET /api/connect`, `POST /api/connect/codex/device|codex/key|claude|claude/code|cancel`, `GET /api/mcp`, `POST /api/mcp/add|remove|share`.

  Repository servers can also be added directly to GPT. For a claude.ai connector, "Connecter à GPT" registers the URL reported by Claude under a Codex-compatible name; Claude's authentication is not copied. Use "Se connecter" on the GPT server if it needs OAuth. This requires an endpoint compatible with Codex's streamable HTTP transport and its authentication; not every claude.ai connector necessarily supports it. SSE servers and Claude HTTP headers cannot be copied to Codex by this flow.

### Agent orchestration

"Nouvelle session → Maître" starts a **master** session: it does not code, it plans the goal in phases, launches **agents** (separate Claude sessions in tmux, each with its own model, effort, permission mode and skills), follows them, unblocks them, checks and integrates their work and reports to you. Its rules live in the `orchestrate` skill (`skills/orchestrate/SKILL.md`), and it drives its team with `bin/orchestrate.js` (`status`, `plan`, `skills`, `launch`, `read`, `send`, `stop`, `resume`), which calls the cockpit API as the calling session (`CLAUDE_CODE_SESSION_ID`).

- **The tree.** A master opens on its "Orchestration" tab: a full canvas with the tree master → phases → agents → sub-agents (or grouped by agent), links coloured by state, collapsible branches and zoom. An agent its orchestrator has closed (stopped) is never drawn; a finished one stays and "Masquer les terminés" hides those. Clicking a node opens a floating inspector: the master's goal, settings and event log; an agent's settings, brief, files, its permission prompt, its conversation and last report, a box to write to it, stop or relaunch. `e` opens a floating box to write to the master; Pause and Réglages (autonomy, active-agent limit, agents' permission mode, token budget per agent, end) sit on the canvas. The ⋯ menu of any running session can promote it to master.
- **Waking up.** After launching agents the master ends its turn. When an agent ends a turn, the background loop queues a short report for its master (or its parent agent); several reports arriving together are merged into one message. The master stays "working" on its card while any of its agents works.
- **Where agents work.** In the master's worktree by default; with `--isolated`, in a new worktree on a branch made from the master's `HEAD` (`<branch>--wN`), which the master merges.
- **Questions.** Agents never ask you: a blocked agent ends its turn with "BLOQUÉ : …" and the master answers it, or asks you depending on its autonomy level (only when blocking, at key steps, or at every decision). Permission prompts of agents still reach you.
- **Permission mode of the whole team.** A new orchestration starts in auto mode, the master included (the "Permissions des agents" choice of the new-session form and `agentMode` of the settings). Changing the agents' permission mode in Réglages applies to everyone, at any depth, not only to later launches (saving the same mode again touches nothing). Each agent stores the new mode (a resume always passes `--permission-mode`, `default` included) and is reached the safest way for its state: an idle Claude prompt gets Shift+Tab one press at a time, the footer read back and the session checked idle before every press (in a dialog Shift+Tab confirms the choice, so a session that works is never pressed); a session with a message waiting in its queue is left for its next turn, no queued message is sent to a session while it is being walked through the cycle, and a walk cut short by a new turn is reported and kept pending; it stops at the target, or relaunches with `--resume` when the target is not in that session's cycle (auto may be missing), and never rests on bypass; an agent blocked on a permission prompt is relaunched with `--resume <session> --permission-mode <mode>` and told the mode changed, its conversation kept; a GPT agent is relaunched the same way once idle or blocked (Codex has no live switch); a stopped agent only stores it. A relaunch is refused before anything is killed when the orchestration is paused, over its agent limit or the worktree is gone; one that fails after the kill is reported to the master, and after a relaunch the screen is read back: a mode different from the target is reported and stays pending. An agent that works, a question dialog, an agent still starting are marked pending (⏳ in the tree) and switched when the turn ends, or relaunched if a permission prompt comes first; an agent that finished its turn is never woken for it. The master is never restarted: its prompt is cycled once idle. The settings event and the toast say how many agents were updated. Agents launched afterwards, by the master or by an agent, take the current mode; `orchestrate launch --mode` is accepted only when stricter than it (plan, or default under accept-edits), and such an agent keeps its own mode when the setting is loosened. A new autonomy level is never pasted into a session: every live agent gets it with the next message it receives, a stopped one in its rules on resume, and the settings event counts both separately; agents' rules name their real parent (master or agent), carry the autonomy level, and only mention sub-agents when the depth limit allows them.
- **Claude/GPT balance.** A master balances the providers by quota, not by agent count: `orchestrate balance` shows how full each provider's usage windows are (7 days first; the 5 hours window only breaks a tie or rules a provider out at 90 %) and the one to favor next. It names the less full account, avoids a provider at 90 % of a window (unless the other is as full) and the one whose quota burns faster per unit of work (measured in tokens, or in agents when tokens are missing); on a tie it alternates. The `pick-agent-model` skill turns it into rules: compare the best Claude and GPT picks, decide by balance when their scores are close (a guideline of about 10 points, not enforced by the code) or the GPT one is `à éprouver`, split fan-outs across both.
- **Agent token budget.** The `agentTokenBudget` setting (Réglages, in millions of tokens per agent, 15 by default, 0 for no cap, 500 at most) bounds what one agent may cumulate, cache reads included (same total as the Usage view): its whole context is re-read at every turn, so a long-lived agent resumed at each iteration costs far more than a fresh one. Past it the tree shows a badge, `orchestrate status` adds `⚠ <tokens> > budget <budget>` to the agent's line, its wake-up message says not to `send`/`resume` it, and `orchestrate send`/`resume` print the same warning (they are not refused). The master is told to relaunch the work in a new agent with a short handover (goal, state, what is left).
- **Limits.** The cockpit refuses launches beyond the maximum number of active agents (10 by default, 20 at most), beyond the depth setting (`maxDepth`, 2 levels by default, 4 at most; an empty value keeps the default), while the master is paused, any permission mode that skips permissions, and any launch by a GPT agent (only Claude agents orchestrate). A child never has a looser permission mode than its parent: it inherits the parent's stricter launch override, and a resume re-checks it against the parent and the orchestration. A resume or a mode relaunch checks only the active-agent limit, never the depth, so lowering `maxDepth` never strands an agent that is already deeper. Pausing holds the reports and hands them over on resume.
- **API.** `POST /api/orch/start|promote|plan|launch|stop|resume|send|pause|settings|end`, `GET /api/orch?caller=`, `/api/orch/read?caller=&id=`, `/api/orch/skills`. The state is in `~/.claude/worktree-orchestration.json` and in the snapshot's `orchestrations` (per master: phases, current phase, `activePhases` (0-based indices of the phases with unfinished agents, sorted, possibly beyond the plan after a re-plan), state, counts, agents with live status and last action, events).

### Review and delivery

- **Diff comments.** In "Changements", `+` on a line adds a comment; "Envoyer à Claude" sends all pending comments as one structured message. Report blocks have "Faire corriger par Claude" and "Voir dans le diff".
- **PR and CI.** With `gh` logged in, each card shows its PR (number, draft, CI running or failing, changes requested, ready, merged), refreshed every minute. A PR tab lists checks, reviews and a "ready to merge" banner, and sends a failing check's log to Claude. "Pousser et ouvrir la PR" pushes the existing commits (no add, no commit) and opens the PR from a template with the configured labels and assignee, then checks them and the absence of a generated footer.
- **Review board.** With `reviewBoard` set and `gh` holding the `read:project` scope, the top bar shows two pills read from a GitHub Projects board every 3 minutes: the open, non-draft pull requests of others in a "to review" status, and your own pull requests in a "needs an answer" status. A click lists them with a link to each PR and to the board.
- **Review claim.** With `reviewClaim` set and `gh` holding the `project` scope, starting a review session on a pull request makes you its Owner on a GitHub Projects board and moves its status to "In Review" (only pull requests carrying `reviewClaim.label` when it is set). A PR that is not on the board is left alone and nothing is claimed: the cockpit never adds one. The write is checked by reading it back; when it fails, the session still starts and a warning says why.
- **Merge a worktree into another.** "Fusionner dans…" (session menu ⋯ or palette) hands a clean worktree over to another worktree of the same repo, then archives it: the target's live session receives the context (branch, unpushed commits, last answers, transcript paths), queued if it is waiting; a stopped target session is resumed first; a target without a conversation starts a new session with it. Only the target keeps working; the merged worktree can still be restored from the archives.
- **Archive and cleanup.** "Archiver" stops the sessions and removes the worktree but keeps its branch and conversation; archived worktrees can be restored, with their session resumed. "Outils → Nettoyage" lists every worktree with its idle time, disk size and git state, for bulk archive or close (close only for merged branches).
- **Serve the app from a worktree.** "Servir l'app" checks the main checkout out on the worktree's last commit (detached HEAD) and restarts the app; "Revenir au checkout principal" puts it back. Refused when the main checkout has uncommitted changes.
- **History.** "Outils → Historique" lists and searches every past session of the repo (messages and edited files), opens it read-only, resumes it in tmux (recreating its worktree from the branch if needed) or starts a new session with its context.

"Outils" also picks the theme: system, light or dark (the "atelier" palette: warm ground, saffron for what waits for you, jade for what is ready to review, slate for what is working, violet for orchestrators).

No npm dependency and no build step: Node, git and tmux only (`gh` for the PR features).

## Install

1. Clone into `~/.claude/cockpit`.
2. Copy `cockpit.config.example.json` to `cockpit.config.json` and fill it in (optional, see below).
3. Run `~/.claude/cockpit/start.sh`. Through `install.js` it merges the missing `settings.snippet.json` entries into `~/.claude/settings.json` (backup `settings.json.bak-cockpit-<timestamp>`, existing hooks and an existing `statusLine` are kept), links `skills/*` into `~/.claude/skills/` and generates the access token. It is idempotent and runs on every start; later starts are automatic through the `SessionStart` hook.
4. Claude Code loads hooks when a session starts, so sessions already open do not report to the cockpit: quit each one (`/exit`) and reopen it with `claude --resume`. New sessions need nothing.
5. Open the URL printed by `start.sh` (`http://<host>:8052/?token=…`).

`cockpit.config.json` is git-ignored. Every key is optional; `${VAR}` in a value is replaced by that environment variable.

## Security

- Access token: `install.js` generates a 256-bit random token in `token` (mode 600, git-ignored). The page stores it in its own `localStorage` (not a cookie, which other apps on the same host would receive), removes it from the URL and sends it as `X-Cockpit-Token` on every API call. It is compared in constant time. Rotate it with `rm ~/.claude/cockpit/token && ~/.claude/cockpit/start.sh`.
- Host allowlist: every request, the page included, is refused with a 421 unless its `Host` is `localhost`, `127.0.0.1`, `$MACHINE_HOSTNAME` or listed in `hosts` / `COCKPIT_HOSTS`. This blocks DNS rebinding.
- Write routes also require a `POST` with the `X-Cockpit: 1` header and a same-origin `Origin`.
- Outside a container the server listens on `127.0.0.1` only.

## Notes

- Only sessions running in tmux can be driven; others are read-only. "Reprendre dans le cockpit" reopens a read-only session in tmux with `claude --resume`.
- A session counts as running in tmux when its state file names a live pane, or when Claude Code's own registry (`~/.claude/sessions/<pid>.json`) maps it to a live pane and its process is alive. The second check keeps a session drivable after the same conversation was resumed in another terminal.
- Sessions with no message (no transcript) are hidden unless they are running, and so are sessions whose worktree directory was removed.
- `index.html`, `web/` and `server/` are read at startup: after editing them, click "Recharger le cockpit" (it reruns `start.sh`) or rerun `start.sh`.
- The server keeps its own data in `~/.claude`: `worktree-events.json` (notifications), `worktree-queue.json` (queued messages), `worktree-links.json` (delegations), `worktree-archive.json`, `worktree-automations.json`, and `worktree-app-serve.json` (app served from a worktree), and `worktree-orchestration.json` (masters, their phases, agents and events), `worktree-matrix.json` (local edits of the relevance matrix) `worktree-matrix-ratings.json` (frozen local 1-5 ratings, read only), `worktree-matrix-verdicts.json` (local verdict records) and `worktree-matrix-coverage.json` (coverage queue); the maintainer's cockpit uses none of them except the coverage queue.
- Only one server should run its background loop at a time. `start.sh` turns it on with `COCKPIT_TICK=1`; an instance started directly with `node server.js` (a test instance) does not send queued messages, run automations or record events.

## Uninstall

1. Remove the cockpit entries from `~/.claude/settings.json` (the `statusLine` and the hooks pointing to this directory), or restore the `settings.json.bak-cockpit-*` backup written by the install.
2. Remove the skill links: `for s in ~/.claude/cockpit/skills/*; do rm ~/.claude/skills/"$(basename "$s")"; done`, and the repo's `.worktreeinclude` if the install wrote it.
3. Stop the server (`kill "$(cat ~/.claude/cockpit/server.pid)"`) and delete `~/.claude/cockpit`. `~/.claude/worktree-state/`, `~/.claude/worktree-reviews/`, `~/.claude/worktree-usage/` and the `~/.claude/worktree-*.json` data files can be deleted too.
- Claude Code auto mode refuses edits to `~/.claude/settings.json` and to the tmux driving code: switch to the default permission mode first.
